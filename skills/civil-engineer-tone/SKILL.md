# 토목 엔지니어 어투 스킬 (civil-engineer-tone)

토목 설계·계획·건설관리 실무 문서의 **문체, 기호 체계, 용어, 수치 표기**를 재현한다. 문체·기호·단위는 전 부문 공통이고, 전문 용어만 부문별로 다르다.
원칙은 하나다: **내용은 그대로, 형식은 현업 엔지니어처럼.** 수치·사업명·근거는 사용자가 준 것만 쓰고, 없으면 `○○`, `[확인 필요]`로 비워 둔다.

## 0. 먼저 판단할 것

1. **작업 모드**
   - `작성`: 메모·요점을 받아 새 문서를 쓴다.
   - `윤문`: 일반 문장/AI 문장을 실무 문체로 바꾼다.
   - `점검`: 이미 쓴 실무 문서의 용어·단위·종결을 검사하고 지적한다(바꾸지 않고 목록으로).
2. **부문** — 입력의 용어로 부문을 정하고 `references/divisions/`의 해당 팩을 읽는다(물산업 `water.md`, 교통 `transport.md`, 인프라 `infra.md`, 도시 `urban.md`, 에너지 `energy.md`, CM·건설 `cm.md`, 지원 `support.md`). 여러 부문이 섞이면 해당 팩을 모두 쓴다. 건축은 `water.md`, 기계·전기·계측은 `energy.md`, 공항·교통 분석은 `transport.md`, 조경·레저는 `urban.md`에 있고, 측량·공간정보는 전 부문 공통이라 `references/glossary.md` 7절에 있다. 어느 팩이든 사용자가 쓴 표현이 우선이다.
3. **문서 유형** — 어투가 유형별로 완전히 다르다. 유형을 먼저 정하고 그 규칙만 적용한다.

| 코드 | 문서 유형 | 기본 종결 | 기본 형식 |
|---|---|---|---|
| R | 보고서 본문(기본계획·실시설계·기술진단) | `~한다`, `~하였다`, `~판단된다`, `~실정이다` | 서술문 + 표 |
| S | 설계기준·시방·과업지시서 | `~한다`, `~을 원칙으로 한다`, `~에 따른다`, `~하여야 한다`, `~할 것` | `○` 조항식 |
| B | 보고 장표(착수·중간·최종보고 PPT), 요약서, 협의자료, 사업설명자료, 회의록, 실정보고 | 명사형 `~수립`, `~필요`, `~검토`, `~예정` / `~임`, `~함` | `□ → ○ → - → ·` 개조식 |
| C | 검토의견서·자문의견·VE 검토(지적하는 쪽) | `~제시 필요`, `~검토 필요`, `~하기 바람`, `~상이함`, `~불일치`, `~검토됨` | `∘ (소제목) 내용`, `· 쟁점 / · 질의` |
| A | 조치계획서·조치결과서(답하는 쪽) | `~반영하였음`, `~반영하겠음`, `~판단됨`, `~사료됨`, `~할 것임` | 보완사항/조치결과/비고 표 |
| V | 설계VE·경제성 검토 제안명 | `~하자` (청유형) | 제안 No. 표 |
| P | 발표 시나리오(구두 보고) | `~보고 드리겠습니다`, `~되겠습니다`, `~입니다`, `~사료됩니다` | `○` 한 줄씩, `/` 끊어 읽기 |
| M | 내부 보고·메일·업무연락 | `~하였습니다`, `~예정입니다`, `~검토 부탁드립니다` | 짧은 개조식 + 1~2문장 |
| G | 공문(시행문) | `~제출하오니 검토하여 주시기 바랍니다`, `~알려드립니다`, `끝.` | 수신·제목·관련·붙임 |

유형이 불분명하면 입력 형식으로 추정한다(표·조항 → S, 장표 문구 → B, 의견 대응표 → A). 그래도 모르면 R로 쓰고 한 줄로 알린다.
유형별 세부 관례(공문 머리·꼬리, 회의록 머리표, 과업지시서 책임 문구, VE 쟁점·질의 구조)는 `style-taxonomy.md`의 L 범주에 있다.

**기호 세트**: 한 문서에서는 하나로 통일한다. 장표·발표는 `□ ○ - ·`, 조치계획서·검토의견서는 `□ ∘ - ·`(실무에서 `∘`가 가장 많이 쓰임), 보고서 본문은 장·절 번호 + `-`·`∙`.
**요청 경어**: `~바랍니다`, `~주시기 바랍니다`는 의견서·조치표·공문 어디서나 쓴다. 위반이 아니다.

## 1. 작업 절차

1. **유형·모드 확정** (위 표).
2. **사실 고정**: 입력의 수치, 단위, 사업명, 기관명, 연도, 법령·기준명을 목록으로 뽑아 둔다. 이후 단계에서 바꾸지 않는다. 단, 단위 **표기법**은 3단계에서 통일한다(값은 유지).
   - 계획/완료, 의무/허용, 부정·조건, 당초/변경의 대상 연결도 유지한다. `반영 예정`을 `반영하였음`으로 바꾸지 않는다. 수치가 있거나 유사 성과품을 참고하면 `references/source-preservation.md`에 따라 원문과 대조한다.
3. **문체 적용**: `references/style-taxonomy.md`의 패턴을 해당 유형에 맞게 적용한다. 핵심만 요약하면:
   - 기호 위계: `□`(대항목) → `○`/`❍`(중항목) → `-`(세부) → `·`/`‧`(나열) / 보충은 `※`, `주)`, `*`, `**`, 출처는 `자료)`.
   - 괄호 소제목: `○ (계획수립 이력) ~ 제시 필요`, `□ (사업내용) ~`.
   - 시점어: `금회`, `당초`→`변경`, `기존`, `기승인`, `기반영`, `상위계획`, `본 과업`, `본 계획`, `상기`, `향후`.
   - 근거 인용: `「하수도설계기준(2019, 환경부)」에 의거하여`, `수도법 제4조에 따라`, `상위계획인 「○○군 하수도정비 기본계획(변경)(2025.06, ○○군)」`.
   - 판단 표현: `~것으로 판단된다`, `~것으로 검토되었다`, `~것으로 나타났다`, `~할 필요가 있다`, `~이 시급한 실정이다`.
   - 결론 전개: 현황 → 문제점 → 개선방안(대안 비교: 경제성·시공성·유지관리성) → `따라서 ~을 채택하였다`.
4. **용어·표기 정규화**: `references/glossary.md`와 `references/units-and-notation.md`를 따른다. 예) `m3/day`→`㎥/일`, `지름 400mm`→`D400mm`, `길이 13km`→`L=13.0km`, `2억 감소`→`△200백만원`, `수도관`→`상수관로`, `하수 파이프`→`하수관로`.
   - 문맥에 따라 답이 갈리는 단어는 `references/lexicon.json`의 `note`를 보고 고른다(예: `물탱크`는 공급용이면 배수지, 정수장 안이면 정수지).
5. **골격 맞추기**(작성 모드): `references/document-templates.md`의 해당 유형 골격을 쓴다.
6. **자체 점검**: 결과를 파일로 저장해 스크립트를 돌린다. 경로는 이 SKILL.md가 있는 폴더 기준이며 표준 라이브러리만 쓴다.
   ```bash
   python scripts/fix_notation.py 결과.md --write      # 단위·수치 표기 자동 교정(값 불변)
   python scripts/check_tone.py 결과.md                # 유형 자동 판별 + 위반 목록 + 등급(A~D)
   python scripts/check_tone.py 결과.md --type C --min-grade A
   ```
   - 입찰 안내서·평가 기준·서약서처럼 원래 경어로 쓰는 지원 업무 문서는 `--type M`(또는 공문이면 `G`)으로 점검한다. 자동 판별에 맡기면 경어체가 위반으로 잡힌다.
   - 등급 A가 목표다. S1이 남으면 반드시 고치고, S2는 고칠 수 있으면 고친다. S3는 원문이 그렇게 썼으면 둔다.
   - 자동 판별 유형이 의도와 다르면 그 자체가 신호다(예: 보고서 본문을 썼는데 `B`로 나오면 서술문이 부족하다).
   - 스크립트를 실행할 수 없는 환경이면 아래 체크리스트로 대신한다.
7. **원문 대조**(윤문 모드): 수치가 있으면 `python scripts/check_values.py 원문.md 결과.md`로 숫자·단위의 변경 후보를 확인한다. 파일은 수정하지 않으며 종료 코드 1은 대조 필요, 2는 입력 오류다. 차이 미검출이나 문체 A등급을 사실 검증 완료로 해석하지 않는다. 표의 대상 연결·부정·의무·완료 상태는 원문과 별도로 대조한다.

### 점검 모드 출력

`점검`을 요청받으면 원문을 고치지 말고 `style-taxonomy.md` 끝의 "위반 판정 출력 형식"으로 목록을 낸다. 스크립트 결과가 있으면 그것을 근거로 하되, 스크립트가 못 보는 항목(당초/변경 대비 누락, 근거 미제시, 전개 순서)을 사람 눈으로 덧붙인다.

## 2. 출력 규칙

- 마크다운 장식(굵게, 이모지, `###` 남발)을 쓰지 않는다. 실무 문서는 HWP·PPT로 옮겨지므로 **기호(□○-·※)와 들여쓰기**로 위계를 표현한다. 표는 마크다운 표 허용(HWP 붙여넣기용).
- 표에는 `<표 3.2-1>` 형식 번호, 우측 상단 `(단위 : ㎥/일)`, 하단 `자료) 상수도통계(2024, 환경부)`를 붙인다.
- 숫자는 천 단위 콤마, 금액은 `백만원`/`억원`/`천원` 중 문서 내 하나로 통일한다. 감소는 `△`, 증가는 `증` 또는 `+`.
- 날짜: 본문 `2026. 11.`, `2026. 11. 19.`, 표·이력 `2026.11.19`, 연도 약기 `’29년`. 기간 `2026. 4. ~ 2027. 3.(360일간)`.
- 윤문 결과 뒤에는 **변경 요약**을 3~6줄로 붙인다(무엇을 왜 바꿨는지, 확인 필요 항목). 사용자가 원문만 원하면 생략한다.

## 3. 하지 말 것

- **내용 창작 금지**: 수치·법 조항·기준 연도·기관 결정을 지어내지 않는다. 모르면 `○○`, `[확인 필요]`.
- **AI 티 금지**: `혁신적인`, `획기적인`, `다양한 측면에서`, `중요한 역할을 합니다`, `결론적으로`, `~것이 중요합니다`, `~할 수 있을 것입니다`, 감탄·수사 의문문, 세 단어 운율 나열. 자세한 목록은 `style-taxonomy.md`의 K 범주.
- **과잉 교정 금지**: 실무 문서에서 관용으로 쓰는 `~에 있어서`, `~에 의거하여`, `~토록`, `~하여야 한다`, `Sheet Pile`, `OPEN CUT`, `Data`처럼 업계에 굳은 표현은 번역투라고 지우지 않는다.
- **유형 혼용 금지**: 보고서 본문(R)에 `~입니다`를, 발표 시나리오(P)에 `~하였음`을 섞지 않는다. 장표(B)에 긴 서술문을 넣지 않는다.
- **기관명 시점 혼동 금지**: 기준·지침 인용은 발간 당시 기관명(예: 「하수도설계기준(2019, 환경부)」)을 유지하고, 현재 주체를 말할 때는 문서 작성 시점의 기관명을 쓴다. 기관 개편 여부가 확실하지 않으면 사용자 입력을 따른다.

## 4. 체크리스트 (출력 전)

- [ ] 문서 유형 하나로 종결어미가 통일되었는가
- [ ] 기호 위계(□ ○ - ·)가 깨지지 않았는가
- [ ] 단위가 `㎥/일`, `D○○○mm`, `L=○○m`, `ℓ/인·일`, `백만원` 등으로 통일되었는가
- [ ] 당초/변경, 금회/기존 대비가 필요한 곳에 들어갔는가
- [ ] 근거(기준명·연도·기관, 법 조항)가 원문에 있는 만큼만 들어갔는가
- [ ] 원문에 없는 수치·사실이 생기지 않았는가
- [ ] 계획/완료·의무/허용·부정·조건과 당초/변경의 대상 연결이 유지되었는가
- [ ] AI 상투어가 남아 있지 않은가
